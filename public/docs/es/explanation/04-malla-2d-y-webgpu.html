El subsistema de malla 2D y WebGPU ​

El trabajo experimental de tránsito superficial: cómo se genera la malla 2D, se acopla a la red 1D, se serializa en el INP, se renderiza y finalmente se reimplementa en la GPU como un marcher WGSL.

Conviven dos generaciones:

  1. Generador de mallas legado (mesh2d.js) — triangulación poly2tri por subcuenca con una escalera de fallback de recorte de orejas (ear clipping).
  2. Pipeline Triangle de producción (mesh2dPslg.js + mesh2dTriangle.js + mesh2dTerrain.js) — Delaunay restringido sobre todo el dominio vía el Triangle WASM de Shewchuk vendorizado.
  3. Marcher WebGPU (public/webgpu/) — una reimplementación WGSL del solver explícito local-inercial del motor, ejecutado en paralelo a (y como alternativa de) el solver 2D WASM.

Fundamentos de coordenadas — mesh2dProj.js ​

Toda la geometría de la malla usa metros locales relativos a un centroide origen con una aproximación equirrectangular: makeTransform(origin) (mesh2dProj.js:16); METERS_PER_DEGREE_LAT = 111320; lng escalado por cos(lat). originFromModel(Net) (:43) = centroide de los vértices de nodos + subcuencas. No es una proyección real, pero es adecuada para dominios a escala de kilómetros.

El modelo de datos de la malla — Net.setIndexedMesh (network.js:874) ​

js
mesh2DIndexed = {
  origin: { lng, lat },
  vertices: [{ x, y, z, lng, lat, tag, nodeId }],       // local metres + geo + rim Z
  triangles: [{ v:[i0,i1,i2], n, tag }],                // n = Manning's, tag = subcatchment id
  vertexNodeMap: [{ vertexIndex, nodeId, cd, area }],   // 1D↔2D coupling rows
  nodeVertexIndex: { nodeId → vertexIndex },
  options: { solver + coupling options }
}

El array legado de celdas Net.mesh2D[] (anillos cerrados, ids estables M2D_<i+1>) se deriva de él para las capas del mapa. inpParser.js:496-519 rehidrata la misma forma desde el .inp.

Construcción del PSLG — mesh2dPslg.js ​

Mesh2DPslg.fromNetwork(sources, opts) (mesh2dPslg.js:128) construye el PSLG de Triangle en fases numeradas:

  1. Borde (:185): se proyecta un polígono GeoJSON, se simplifica con Douglas-Peucker (dpSimplify, :53) y se densifica (densify, :84); segmentos de restricción con marker=1; región de fondo por defecto attr=0. Sin borde, un dominio automático = envolvente convexa (convexHull, :116) amortiguada por domainBuffer (50 m por defecto).
  2. Subcuencas (:271): cada una se convierte en una semilla de región de Triangle (mapeada vía regionAttrToSub) y opcionalmente en un anillo de restricción (marker=2) cuando useSubRings.
  3. Nodos (:292): los nodos hidráulicos se vuelven vértices Steiner etiquetados con su id de nodo (imponiendo minNodeSep); con useRimZ, la Z del vértice = invertEl + maxDepth (brocal).
  4. Conductos (:327): los trazados de conductos se vuelven segmentos de restricción con marker=100+k único, mapeados de vuelta vía markerToConduit.
  5. Capas de restricción (:349): puntos/líneas/polígonos importados se vuelven vértices/segmentos de restricción (marker=3); los polígonos marcados "bloquear flujo (impermeable)" se vuelven huecos (con una salvaguarda contra "tragarse el dominio").
  6. Dedupe de segmentos (:409) por clave de punto min:max; eliminación de segmentos cruzados (:422) vía un test segsCross con grid de bboxes (buckets de 25 m).
  7. Radio de aplanado (:473): los vértices cerca de un vértice de nodo heredan su Z de brocal (aplanado de cuencas de encharcamiento).
  8. Z de terreno (:502): los vértices restantes reciben opts.sampleZ(x,y).

_addPt (:157) es un insertor de fusión con snap por hash espacial; interiorPoint (:33) elige las semillas de huecos/regiones.

Triangulación y terreno — mesh2dTriangle.js / mesh2dTerrain.js ​

  • Mesh2DTriangle.triangulate(pslg, quality, ctx) (:92) empaqueta el PSLG en arrays Float64/Int32 y corre Triangle con switches: pQAY (PSLG, silencioso, atributos, sin-Steiner-de-borde cuando se pide), q{minAngle} (default 33°), a{maxArea} (default 200 m²) o lista de áreas regionales, S{maxSteiner}. Los vértices de salida se re-mapean con un CoordHash de 1 mm (:21); el n de Manning sale del atributo de región → lookup de subcuenca (manningForSub, :36 — prioridad: clase de cobertura de suelo → nPerv → nImperv → default).
  • runGeneration(sources, quality, ctx, log) (:251) orquesta con presupuestos duros:
    • trianglePointBudget = 8000 puntos (el heap de Triangle WASM está fijo en 16 MB) — los modelos grandes sueltan los anillos de subcuenca + restricciones de conductos y reasignan la rugosidad por centroide.
    • autoAreaCap (:331): el área máxima se limita a domainArea/15000, minAngle se acota a 30°, maxSteiner 30000, Steiner de borde deshabilitado.
    • maxTriangleRegions = 256 (:361): más allá, todas las semillas de región colapsan y los tags/n se asignan por centroide.
    • Fallback al generador poly2tri (:380) ante un fallo de Triangle.
  • Mesh2DTerrain.makeSampler(settings, map) (mesh2dTerrain.js:24): MAPBOX → map.queryTerrainElevation; OPENTOPOGRAPHY_* → API de bbox de OpenTopography; GEOTIFF → readRasters de geotiff.js con interpolación bilineal (:109), manejo de nodata, reproyección proj4 y refreshBounds() exponiendo la huella del ráster como dominio automático.
  • resolveVertexElevations(...) (:123): Z de brocal primero → sampler → fallback IDW (k=4) → 0.
  • thinTerrain(sampler, domain, opts, transform) (:152): adelgazamiento adaptativo de terreno — grid de ≤300×300 candidatos puntuados "más-curvo-primero" por la desviación local de la normal de superficie, aceptados con espaciado mínimo y buffer de borde.

Acoplamiento y serialización INP ​

  • Mesh2DCoupling.buildVertexNodeMap(indexed, nodes, opts) (mesh2dCoupling.js:5) deduplica las filas vértice↔nodo; coeficiente de acoplamiento por defecto cd = 0.65.
  • Mesh2DInp.buildInput(baseInp, cells, map, options) (mesh2dInp.js:162) rechaza las unidades US (:163), prefiere la malla indexada (superponiendo las opciones de solver actuales del diálogo sobre las guardadas, :175-184), y delega en Mesh2DExport.buildInline (mesh2dExport.js:54) o buildExternal (:68, [2D_MESH_FILE] + .2dm).
  • Secciones emitidas: ;; UNITS: SI (m), ;; 2D_ORIGIN lng lat, [2D_OPTIONS], [2D_VERTICES] (X Y Z TAG), [2D_TRIANGLES] (V1 V2 V3 MANNINGS_N TAG), [2D_VERTEX_NODE_MAP] opcional.
  • Mesh2DExport.optionLines (:22) emite las opciones de solver: MAX_TIMESTEP, DRY_DEPTH, COUPLING_CD, COUPLING_SYNC, THETA, CFL_NUMBER, H_MOVE, LTS_TIERS, FROUDE_MAX, LIMITER_EPSILON, FLUX_DH_EPS, CELL_CLOSURE, FACE_RECONSTRUCTION, VFR_MIN_WET_FRAC, INTEGRATOR EXPLICIT, COUPLING_AREA, RAINFALL_MODE opcional, REPORT_2D.
  • El diálogo de malla (mesh2dDialog.js) orquesta todo desde un modal de 3 pestañas (Fuentes/Calidad/Hidráulica): generate() (:369) ensambla las fuentes, el transform, el sampler de terreno, la calidad/ctx, corre Mesh2DTriangle.runGeneration, resuelve las elevaciones, construye vertexNodeMap y llama Net.setIndexedMesh. Los defaults (defaultSettings, :16) persisten en localStorage con migraciones (v4 alinea LTS_TIERS 4, MAX_TIMESTEP 10, H_MOVE 0.003; v5 alinea THETA 0.8, CFL_NUMBER 0.7, FROUDE_MAX 1.5, COUPLING_SYNC 0, FLUX_DH_EPS 0.004, VFR_MIN_WET_FRAC 0.01 — todo según el SolverOptions2D.hpp del motor / Ref Manual Vol II Cap 9 §9.11).

Renderizado de la simulación 2D ​

Dos capas complementarias:

  • Overlays GeoJSON — mesh2dRender.js: Mesh2DLayers.ensure(map) (:95) crea fuentes/capas para puntos de vértices, isolíneas de tirante (isolines, :32), bandas de contorno de tirante (contourBands, :50 — la parte seca se recorta bajo el View2D.DEPTH_MASK_M canónico (5 mm) para que la película de lluvia uniforme quede invisible), flechas de velocidad (velocityArrows, :89, umbral mag < 0.002, tamaño de flecha √(mag/max) acotado 0.4–1.8), y bandas/isolíneas de elevación. onStep(step, frame) (:127) reconstruye el campo de tirantes de vértices (desde frame.vertex.depth o, cuando el motor emite tirantes por celda, ponderado por área y solo con celdas húmedas para que los tirantes húmedos nunca se filtren a vértices secos) en cada cuadro de animación. Expuesto en el árbol de capas (12 toggles).
  • Capa Gouraud WebGL2 — meshGlLayer.js: MeshShadeLayer (:6) es una capa custom de Mapbox (renderingMode:'2d') con shaders GLSL ES 3.0 y una rampa de color de 5 paradas (#2e7dd1 → #26a69a → #ffca28 → #f57c00 → #d32f2f). setField (:16) codifica t = clamp((v−min)/(max−min)) con alpha solo-húmedo. Mesh2DGL.ensure (:18) agrega m2d-smooth-depth-fill y m2d-mesh-terrain bajo el relleno clásico por celda (swmm-2d-mesh-fill, que se colorea por triángulo vía feature-state resultColor, results.js:393/433).

El marcher WebGPU — public/webgpu/ ​

  • webgpuMarscher.js — buildEdges(mesh) (:23) es un port bit-exacto del InertialEdges.cpp del motor (centroide/área/lecho por triángulo, claves de borde por par ordenado de vértices, normales salientes, bordes interiores de Fase 1, cell_lchar = 2·area/xiMax, CSR por celda). WebGPUMarcher (:171) sube buffers SoA empaquetados y compila un pipeline de cómputo con un bind group de 16 bindings (_compile, :338) más 15 pipelines de cómputo. advance(t0,t1,rain) (:592) espeja ExplicitInertialSolver::advance — cadencia de rebuild 4, vía K=1 de dt global, macro-ciclo LTS K>1, dtFloor protege el colapso CFL de velocidad de Perot en f32.
  • shaders/marcher.wgsl (el único archivo de shaders) — un port 1:1 f64→f32 de InertialKernels.hpp. Los parámetros viajan como un array<f32> plano (los storage bindings tipados por struct fallan en algunos drivers). Kernels: faceFlux (actualización de cara local-inercial de de Almeida & Bates + presupuesto de positividad de la celda exportadora β/3·V), cellUpdate (descarga de celda de Perot), lazySources, seedActive (activación histerética h_on = hMove+0.001, h_off = hMove−0.001; celdas de acoplamiento fijadas), halo, couplingExchange (orificio regularizado C¹ Q = cd·Aeff·√(2g)·φ, drenaje limitado por β·V/dt, rebalse limitado por un registro de extracción por nodo), cflReduce/cflArgmin (atomicMin de dt0 bitcast + celda argmin), y el set LTS v2 (settleAcc, tierAssign, faceTierAssign, degenTier/degenFaceTier, faceFluxLts, cellUpdateLts con refire = 2^(tier_exp − face_tier)).
  • couplingSplit.js — la maquinaria del split M2 (segura para workers): parse2DMesh/parse2DOptions (:18/:43), nodeOrder (:67, índice de nodo = orden de parseo entre JUNCTIONS/OUTFALLS/STORAGE/DIVIDERS ordenados por posición global del texto — una caminata fija mal-indexa algunos INPs), buildVertexStencil (:95, pesos de partición de la unidad de Jawahar-Kamath), parseCoupling (:144, clave = (invert+fullDepth)·len12; COUPLING_AREA DEFAULT → A = clamp(1.25·Amax_conduit, 0.05, 2.0) m²; los puntos de vértice resuelven a la celda incidente de lecho más bajo, según SurfaceRouter2D.cpp:394-412), build1DInp (:283, quita las secciones 2D, fuerza ALLOW_PONDING YES, preserva el propio VARIABLE_STEP adaptativo del modelo — un pin previo a 0 corrompía el solve 1D), rainMpsAt (:331, lluvia media de pluviómetros, manejo de INTENSITY/CUMULATIVE/VOLUME), y el núcleo runSplit (:400): llena cada ventana de acoplamiento por tiempo, congela el estado 1D de los nodos en filas cplF de 9 floats, protege el estado no-finito (COUPLING_STATE_NONFINITE), marcher.advance, devuelve ∫Q vía setLatInflow(exch/dtBatch) (igualando la entrega en cola de media de dos ventanas del motor), emite cuadros, calcula el balance de masa real.
  • gpu2dWorker.js — el worker de producción (mismo contrato run2d que openSwmm2dWorker.js): carga el motor WASM solo para la parte 1D, requiere maxStorageBuffersPerShaderStage: 16 (requestGpuDevice, :70; lanza WEBGPU_UNAVAILABLE si no), escribe un INP solo-1D, setPondArea(tri_area) por nodo de acoplamiento, y luego CouplingSplit.runSplit con una ventana de acoplamiento de 60 s.
  • harness.html — página de validación M0/M1/M2. Umbrales: conservación ≤ 0.5 %, tirante medio ≤ 1e-3 m, correlación de Pearson mediana ≥ 0.5; intercambio M2 dentro de 5 %, corr temporal ≥ 0.9.

Límites duros y veredictos honestos registrados en el plan:

  • Apple Silicon / Metal (≤10 storage buffers) no puede correr el backend — 16 storage buffers exceden el límite de Metal; el worker lanza WEBGPU_UNAVAILABLE y la app cae al WASM.
  • La divergencia f32/f64 en max|Δdepth| se acepta; la validación es estadística.
  • Veredicto de rendimiento honesto: el 2D en GPU es rápido (0.13 ms/subpaso) pero la onda dinámica 1D es ~90 % del tiempo de reloj en ambos backends, por lo que el split está actualmente a la par con el motor, no más rápido.
